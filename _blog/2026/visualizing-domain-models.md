"Self documenting code" is a concept mainly relevant for software developers. The self-documenting part in there indicates that no particular documentation is necessary and that all necessary information is effectively conveyed through the codebase itself. In the context of domain driven design - DDD for short - this poses a distinct challenge. While the domain model in code is meant to represent the current understanding of some business, this representation of the domain model is solely accessible to developers. What would it look like if we were to create a feedback loop from the codebase back to everyone involved with the software? What would it look like if code was truly self-documenting in the sense that metadata about its function would be widely available for people to inspect and interact with?

But why would one do that to begin with?  ...........

It should be acknowledged that there are already multiple tools built to visualize codebases (for dotnet: NDepend, nplant). These tools however are built to help developers, not end users of software. What we will find when using these tools as well is that the core meaning intended to be conveyed by the domain model gets lost in a sea of implementation details and coupling to infrastructure. Sure enough it is possible to build a domain model without external dependencies, but that'll leave you in charge for coordinating the lifecycle and management of commands, events, aggregate state and more.   


-- communication & CI but for domain models


What would happen if we were able to generate documentation from code? Not just "self-documenting code". That stuff is meant for the developers -- but instead truly self-documenting systems, generating resources meant to be used by the system' users. The concept of self-documenting code falls short in the sense that this mostly involves basic hygiene. Give variables proper names, convey intent and what not, but none of this generally escapes the boundary of the IDE.

And that is a problem. One idea part of domain driven design, or DDD for short, is that the domain model should represent how people think about the system. Consequently if this were the case the system should also be able to convey back to its operators a more or less accurate representation of the current mental model it represents. Right now this perspective is only beholden to its developers, but what if we could open this up to regular users as well?

Clarke's third law states that "any sufficiently advanced technology is indistinguishable from magic". Modern software is often indistinguishible from magic in the sense that it's complexity is overwhelming to an extent that people without insider know-how cannot even begin to comprehend how a given feature works. Oftentimes by accident or happenstance. Sometimes by design. Sometimes this complexity is a necessity (e.g. due to regulation) and so the question arises; can we spoil the magic?
